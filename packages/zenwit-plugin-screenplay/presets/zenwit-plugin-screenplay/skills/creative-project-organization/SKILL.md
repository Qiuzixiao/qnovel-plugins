# 创作项目规划与归档

让创作者直接开展创作，由 Agent 在写作过程中维护清晰的项目结构。本技能与写作技能共同执行：写作技能决定内容怎么写，本技能决定这些内容如何组织和保存。

## 首批文件：先确定位置，再写内容

用户要求从梗概开始创作、生成一批文档或保存创作成果时，主动执行以下步骤，无需等待用户说“整理文件”。

1. 查看必要范围的项目文件路径，结合已知内容理解现有分组；用途不清时读相关文件。已有信息足够时直接复用。
2. 在第一次写入前，确定本次准备交付哪些文件、各自用途、哪些需要共同维护。结合已明确的后续创作安排，不把当前只有一个文件误当成整个项目只有一个文件。
3. 为这批文件选定具体保存路径，再开始写入。每个路径都应对应文件在项目中的角色。不能先给所有文件填裸文件名，等用户指出混乱再补分类理由。
4. 新分组随首个文件一起创建。规划只覆盖当前交付和已明确的后续需求，不预建整套空目录。

这个规划由 Agent 自行完成，不要求创作者填写配置、编写 PROJECT.md 或批准日常目录选择，也不自动生成一份规划文档。需要交代时，用一句话说明本次产物分别放在哪里，然后继续创作。

## 后续交付：扩展前复核分组

每次新增独立用途的交付物时，先检查它和现有文件的关系，再选路径。不要因为上一份文件在根目录或某个目录，就沿用同一位置。

例如，从一句梗概发展到人物资料、全剧规划，再到几十集集纲时，已成为包含多类持续维护内容的项目。应在新增这些交付物时安排各自位置，而不是沿用最初单份梗概的布局，直到用户要求整理。

已有分组职责匹配则复用；用途不同且需要独立维护则建立合适分组。检查的是归属是否清楚，不是文件夹数量。数字前缀只解决排序，单个万能文件夹也不能代替内容规划。

## 如何判断归属

- 以内容的实际用途、查找方式和更新关系分组，名称跟随用户措辞、项目语言和既有命名风格。用户明确的路径与组织要求优先，没有既有习惯时使用当前创作语言。
- 区分项目总览、写作约束、故事事实、故事推进、正文及支撑材料；这是判断视角，不是固定目录清单。按项目需要决定人物、世界观、资料或修改意见是否独立维护。
- 目录存在不等于适合所有内容。“设定”可以承载相关故事事实，但不能仅因名称宽泛就顺手收纳写作规范、大纲和正文。
- 读内容区分故事内机制和指导作者的规范。“规则书”可能属于世界观，也可能属于创作约束，不能只凭“规则”二字分配位置。
- 根目录是合法位置。选择它时，同样要判断文件是否承担全项目职责，或是否适合当前项目的组织方式；“文件少”“先保存”“名字叫总纲”本身都不足以替代这个判断。用户指定的根目录路径正常执行。
- 相关内容构成完整交付物时可保留在同一文档，以章节或引用组织。只有确实需要独立查找和更新时才拆分，不为分类纯度拆碎用户的综合文档。

## 已有文件与完成检查

原位修改继续使用原路径，不顺手重组旧项目。新增内容按当前用途归档；若发现旧布局影响查找或续写，说明具体整理建议，继续可完成的创作。用户已要求整理时执行必要迁移，修正受影响的引用，检查没有丢失或覆盖内容。

本次交付结束前核对实际路径与预先确定的分组是否一致；如果多种独立用途仍堆在同一位置，重新判断它们是否确实属于一个组，而不是事后统一称为“项目级文件”。简短报告实际产物位置，不让用户承担归档工作。
